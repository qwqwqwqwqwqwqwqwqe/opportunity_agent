# V3 聊天助手

聊天支持新增、修改或删除学校申请项目和待办，新增日程，更新个人画像/偏好，查询已有数据，普通聊天与解释官网通知。整条链路都在聊天中完成：补问信息 → 展示草稿 → 明确确认 → 保存或删除，无需填写表单或打开审批面板。删除前会展示准确目标；目标不唯一时先追问，不会猜测。复用现有会话、SSE、审批和领域服务，无需新数据库迁移。

现已增加 `search` 官网查询：Tavily MCP 返回候选链接后先由用户确认，确认后读取页面并生成带原文证据的回答。使用和配置见 [官网查询说明](CHAT_SEARCH.md)。不会直接用搜索摘要作答或自动导入项目数据。

## 使用

重建当前服务后 Ctrl+F5：

```powershell
docker compose -f compose.applyops.yml up --build -d api worker
```

Compose 默认访问 `http://localhost:8001/v3`；本地脚本默认是 8000。左侧进入「聊天助手」。需要配置可用模型进行业务操作解析；不要把密钥填到聊天中。

- `添加 CMU 的 MSAII，2027 Fall，2026年12月15日截止，需要 SOP、3封推荐信和托福105。再给这个项目添加一条明天截止的“修改SOP”待办，显示在日历。11月2日下午3点到4点见推荐人，也帮我新增日程。`：生成联合草稿，确认后项目显示在总览，待办关联新项目，日历同步显示待办和固定日程。
- `帮我添加一个学校项目`：直接在聊天中补问学校、项目和申请周期，不猜年份；截止日期和材料未知可以不填。
- `根据现有项目材料准备情况生成具体待办，不重复已有任务，先不排日期`：生成任务建议，确认后保存；不把建议当作学校官方要求。
- `新增一个全局待办：整理简历，不设置日期`、`新增日程：明天下午3点见推荐人`：无需表单。
- `把待办截止改到11月3日`：调整尚未提交的草稿，旧审批失效。
- `cmu msml项目的材料要求是一个sop,三个推荐信，托福，可选gre，成绩单，简历，其中gre已经提交，其他都准备好了`：定位已存在的申请，生成修改草稿。回复“确认保存/确认修改”后更新原项目，不重复创建；三封推荐信分别维护状态，GRE 可选且 submitted，其余 ready。只有一个匹配周期时沿用，多周期先澄清。
- `删除 CMU MSML 2027 Fall 这个申请项目`：列出将删除的项目、材料要求、材料、待办、官网监控记录和关联站内信；回复“确认删除”后执行。若同一项目有多个申请周期，会先询问周期。
- `删除“修改 SOP”这个待办`：预览待办标题、所属项目和日期；回复“确认删除”后删除，若它显示在日历也会同步移除。重名待办会先询问所属项目或截止日期。
- 修改默认合并：未提及的 DDL、周期、备注、要求和材料状态保留；已有要求/材料 ID 和推荐人名称不变。明确说“只保留/替换整个清单”才归档其他要求，预览列出将归档的条目。“准备好了”不撤回已有提交，材料已准备也不等于核验了最低分，不修改个人成绩或任务状态。
- `确认添加`、`确认保存` 或 `确认删除`：统一提交当前对话最近的完整提案。删除操作使用单独的“确认删除”提示；回复 `取消` 放弃草稿。重复确认不重复创建或删除；另一个对话不能确认本对话提案。

- `我的托福是105分`：首次录入生成待确认提案，确认之前数据库不改变。
- `我的托福更新为110分`：已有标量不同，沿用 V2 冲突弹窗，选择保留旧值或使用新值后生效。
- `查看我的画像`、`我的托福多少分`：读取当前已保存值，不把待确认信息当作已保存。
- `我目前有哪些申请项目`、`CMU的MSAII还缺哪些材料`：查询用户已记录项目、要求和材料；准备完成不等于已提交，不宣称覆盖学校全部要求。
- `查看1月15日的待办`、`本周有什么日历事项`：按用户当地当前年/日期筛选。带日期的查询不包含未排期事项。
- `我有多少封未读通知`、`解释最新一封官网变化通知`：只读取本人站内信，不标记已读。
- 多封通知且没有明确指定时先澄清；在信箱详情点击「在画像助手中解释」会绑定具体通知，可继续问“这对我意味着什么”。连续追问绑定原通知，不因新信到达而悄悄换成新的“最新”通知。
- `你好`、一般申请准备问题：配置模型后自然回复；没有模型时提供规则查询、画像提取和明确的功能介绍，不冒充真实模型效果。

通知解释引用已保存的分析、当时个人依据和官方证据，不重新抓取官网，不调用个人影响 Agent，也不自动发信。画像改变后需到官网监控重新检查，不能把历史结论理解为最新核验。

## 边界

意图识别已于 2026-10-29 改为一次结构化模型调用，同时返回 `ChatUnderstanding.intent`、`scope`、简短分类依据和操作草稿。主入口不再用“新增/添加”等关键词决定是否调用模型，也不再将未命中的业务请求送去画像提取。意图分为新增操作、画像更新、查询、通知解释、普通聊天、需澄清和不支持的操作。

只有 `intent=profile_update` 才允许进入画像提取；查询、项目创建、模型异常或非法输出均不会回落到画像更新。模型未配置时仅保留既有数据查询和明确画像事实的保守规则能力。严格的“确认添加/取消”控制短语仍由后端识别，避免模型自行批准写入。每次模型分类保存在 Run 的 `intent_recognition`，查询 Run API 可查看。

例如“增加一个cmu msml项目，截止日期11.18”应识别为新增申请项目，保留 CMU、MSML 和原始日期文本 11.18，询问申请周期与截止年份，不生成 `project_experiences` 画像候选；用户补充“2027 Fall，截止是2026年11月18日”后再展示完整草稿。只有月日时不猜截止年份。

- 项目新增/修改、待办和固定日程创建复用 `project.save`、`task.create`、`calendar_event.create`；项目和待办删除使用版本校验的 `project.delete`、`task.delete`。画像/偏好仍使用原有提取与冲突机制。同轮待办可用 `$ref` 关联项目。`projects[].operation=update` + `application_id` + `changes` 表达局部修改；`build_commands` 委托 `chat_project_updates.build_project_update` 合并完整 ProjectForm，并带上服务端快照 revision。
- 草稿持久化到当前对话 AgentRun，刷新后仍可继续。模型只给结构化草稿，后端校验白名单、目标归属、日期和重复项；最终审批复用统一领域服务、幂等回执、事务与 Outbox。
- 聊天已支持修改已保存项目的基础字段、DDL、GRE 政策、材料要求及准备/提交状态，也可新增或删除申请项目和待办。项目删除会清除项目关联的材料、待办、官网监控及信箱通知；保留计划历史快照和删除审计事件。待办删除会从日历投影中消失。固定日程和监控配置仍使用对应页面；自动排期保持停用。任务完成不等于材料准备或提交完成。
- 不初始化 RAG/Research Agent，不生成 SQL 或提供任意工具执行；只有明确 `search` 意图使用独立 Tavily MCP 和经过用户确认的网页读取器。
- 数据查询使用服务端按用户身份构建的快照；通知及其分析/证据按 user_id 校验。复制他人的通知 ID 不会回退到其他信件或暴露内容。
- 模型负责草稿解析/任务建议、查询结果的自然语言组织及普通聊天；不能直接写库或自行审批。提案预览与提交回执由后端生成，只有事务成功才声称已保存。模型不可用或结构非法时不新增业务数据。
- 历史 V3 WorkflowOrchestrator 类仍为旧验收/评测保留，正式 ApplyOps 聊天单例已切换为 ProfileAssistant；V2 入口不受影响。

## 界面

采用与 V3 工作台一致的灰白背景、低饱和绿色、圆角消息卡片和输入框。导航统一为“聊天助手”，欢迎页增加项目、待办、日程快捷示例。聊天提交后同步刷新工作台和其他标签页；已有手动页面保留。
